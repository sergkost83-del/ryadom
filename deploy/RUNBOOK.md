# Развёртывание и эксплуатация «РЯДОМ»

Схема не привязана к провайдеру: Docker + обычный PostgreSQL + S3-совместимое хранилище для копий + SMTP. Платных сервисов эта инструкция не покупает: выбор и оплату сервера, домена и почты вы согласуете отдельно.

## 1. Что нужно
- Сервер в РФ (по требованию хранения данных) с Ubuntu 24.04, 2 vCPU, 4 ГБ ОЗУ, диск 30–40 ГБ SSD, Docker и Docker Compose.
- Домен с A-записью на сервер.
- Почтовый сервис с SMTP (вход по коду идёт через почту). Настройте SPF и DKIM домена, иначе письма уйдут в спам.
- Хранилище для копий (S3-совместимое), лучше у другого провайдера, чем сервер.
- На вашем компьютере: утилита `age` (шифрование копий).

## 2. Ключи (делается один раз, секреты не пересылать)
- **Ключ копий.** На вашем ПК: `age-keygen -o ryadom-backup-key.txt`. Строка `age1...` в файле — публичный ключ (в `.env.prod` как `AGE_RECIPIENT`). **Файл целиком хранить только у себя, офлайн, не на сервере.** Без него копии не расшифровать.
- **Ключ шифрования секретов 2FA.** `docker compose ... run --rm backend python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` → в `FIELD_ENCRYPTION_KEYS`. Сохраните копию ключа отдельно от сервера: потеряете — придётся сбросить 2FA всем сотрудникам.
- **SECRET_KEY.** `python -c "import secrets; print(secrets.token_urlsafe(64))"`.
- **ADMIN_URL.** Придумайте непредсказуемый адрес вида `panel-k3x9q/`.

## 3. Первый запуск
```
git clone <адрес репозитория> /opt/ryadom && cd /opt/ryadom
git checkout tags/<версия>
cd deploy && cp .env.prod.example .env.prod   # заполните все значения CHANGE_ME
docker compose --env-file .env.prod -f docker-compose.prod.yml build
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm backend python manage.py migrate --noinput
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm backend python manage.py load_communities
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm backend python manage.py setup_roles
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm backend python manage.py createsuperuser
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d
```
Проверка: `https://ДОМЕН/api/v1/health/` отвечает `{"status": "ok", ...}`. Затем войдите в админку (`https://ДОМЕН/ADMIN_URL`), настройте двухфакторную защиту и сохраните резервные коды.

## 4. Безопасность сервера
- Брандмауэр: открыты только 22, 80, 443 (`ufw allow 22,80,443/tcp && ufw enable`). Порт базы наружу не публикуется.
- SSH только по ключам, вход по паролю и под root отключить. Включить автоматические обновления безопасности (`unattended-upgrades`).
- Файл `.env.prod` доступен только владельцу (`chmod 600`).
- Админка закрыта двухфакторной защитой; при желании ограничьте её по IP в `Caddyfile` (пример в комментарии).

## 5. Резервные копии
- Ежедневно (cron, см. `crontab.example`): `pg_dump` → сжатие → шифрование `age` → внешнее хранилище. Копии старше 30 дней удаляются (срок хранения персональных данных в копиях; согласуйте с юристом).
- **Раз в месяц проверяйте восстановление** (учение): скачайте свежую копию, затем `AGE_IDENTITY_FILE=/путь/ключ.txt docker compose ... --profile tools run --rm --entrypoint restore-drill.sh backup /путь/копия.sql.gz.age`. Скрипт восстановит копию во временную базу, посчитает таблицы и пользователей и удалит её.
- Восстановление боевой базы: остановите `backend`, затем `CONFIRM_RESTORE=yes AGE_IDENTITY_FILE=... restore.sh <копия>` (перезапишет базу), запустите `backend`.

## 6. Обновление и откат
- Обновление: `deploy/update.sh v0.9.0` (делает копию базы, собирает, применяет миграции, перезапускает).
- Откат кода: `deploy/rollback.sh` (на предыдущую версию) или `deploy/rollback.sh v0.8.0`. Миграции пишутся так, чтобы предыдущий код работал на новой схеме; если это не так, восстановите базу из копии, сделанной перед обновлением.

## 7. Переезд на другого провайдера
1. Поднять новый сервер, поставить Docker, склонировать репозиторий на тот же тег.
2. Заполнить `.env.prod` (те же ключи `FIELD_ENCRYPTION_KEYS` и `DJANGO_SECRET_KEY`).
3. Остановить запись на старом сервере (`docker compose stop backend`), сделать последнюю копию.
4. Расшифровать копию на вашем ПК или на новом сервере, восстановить в новую базу.
5. Запустить, проверить `health` и вход.
6. Переключить A-запись домена. После проверки удалить данные на старом сервере.
Репетируйте переезд заранее на временной машине: так вы узнаете, что копии действительно работают.

## 8. Ежедневные задачи
В cron: копия (02:30) и `purge_expired` (03:30): очистка кодов, токенов, счётчиков, стирание аккаунтов с истёкшим сроком удаления.

## 9. Если что-то сломалось
- Логи: `docker compose ... logs --tail=200 backend`.
- Потерян телефон и коды у сотрудника: главный администратор сбрасывает его защиту в разделе «Пользователи». У самого главного администратора: `docker compose ... run --rm backend python manage.py reset_2fa <e-mail>`.
- Подозрение на утечку: смените `DJANGO_SECRET_KEY` (выйдут все сессии), пароли базы и почты, ключи доступа к хранилищу; для персональных данных действуют сроки уведомления Роскомнадзора (уточнить у юриста).

## 10. Перед публичным запуском с реальными жителями
Уведомление Роскомнадзора, политика и согласие (тексты юриста), сервер, копии и почта в РФ, проверка восстановления, проверка SPF/DKIM, тест нагрузки сценария «чат дома» (после M2), фиксация версий зависимостей.
